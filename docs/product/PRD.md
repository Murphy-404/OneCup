## 1. 定位与目标

面向家庭饮品爱好者、希望自主保管记录的用户以及自部署维护者，提供不依赖公共社区的饮品制作工具。

核心任务：**找到配方 → 核对材料和器具 → 解决缺料 → 按步骤制作 → 私人保存 → 再次复现**。

开源版本身是完整产品，不能通过缺失关键制作能力、强制注册到自营服务或跳转付费服务来制造使用门槛。公开源码的目标是可运行、可理解、可维护，而不是只公开一个前端外壳。

首版成功标准是上述任务及独立部署验收通过；后续观察有同意基础的任务反馈和缺陷，不以站内关系、内容发布量或社区活跃衡量。

## 2. 产品边界

### 包含

- 无登录单用户实例，个人记录保存到服务端 SQLite；Docker 使用命名数据卷，支持一致性快照、JSON 导出、恢复和旧本地记录迁移。
- 参考配方、材料与器具库、有条件的自制和近似替代。
- 自建配方、个人改编版本、私人配方合集、收藏和多杯备料。
- 咖啡参数工具、完整图片预览、JSON 备份和恢复。
- 可阅读的源码、示例数据、配置、测试和自部署说明。

### 不包含

- 公开昵称、头像上传、作者主页、用户作品目录、站内公开链接和合集分享页。
- 公开动态、关注、粉丝、评论、点赞榜单、私信和用户关系数据。
- 社交发布与审核表、对应 API、第三方社交 SDK、自营运营面板和遥测依赖。
- 自营真实用户、邮箱、数据库文件、历史导出、真实密钥及个人联系资料。

本版同时排除账号登录、服务端账号数据库与运营云同步。自营版的身份、邮件、会话与同步能力不进入个人版。

## 3. 运行模式

Node.js + SQLite 或 Docker Compose 自托管；也支持 Cloudflare Workers + D1 持久托管，默认公开只读模式，写入须明确开放并限制可信访问。每个实例只有一份工作区，无账号隔离；不同设备和浏览器访问同一实例共用记录。默认只绑定回环地址，远程使用需可信网络或带访问控制的 HTTPS 反向代理。

浏览器不承担权威持久存储。Docker 容器替换保留命名卷；删除卷、磁盘损坏仍会丢失数据。默认启动时及每 24 小时生成一致性快照，并要求用户定期离机备份。旧浏览器数据主动导入并确认替换，旧账号数据库不直接复用。

## 4. 信息架构与界面

- **发现**：顶部导航、居中配方卡片网格、搜索、分类、主动随机，高级筛选收起。
- **我的材料**：材料、器具、状态与咖啡参数入口。未登记与没有分开，水和冰不默认有。
- **我的做法**：收藏、私人自建/改编配方、私人合集；不出现作者主页或发布按钮。
- **配方详情**：完整图、规格、用量、器具、缺料路径、步骤、验证状态和私人编辑入口。
- **制作模式**：当前步骤与用量，材料/器具切换，切步、计时及完成；仅内容区滚动。
- **备料**：全局快捷入口，按配方和份数合并用量；不是公开合集。

默认配色沿用白绿方案；移动端至少 320px 宽可操作，常用触控目标至少 44px，尊重减少动画与浏览器缩放设置。

## 6. 核心流程与需求

### 6.1 参考配方与缺料解决

未登记库存也能打开配方。筛选、随机、准备路径使用同一条件来源；不把拥有豆子视为已有咖啡液，不将 ml 与 g 无依据互换。近似方案明确改变的香气、浓度、甜度或泡沫，自制方案记录实际投入与产量。

采用方案须用户主动操作；材料、步骤、器具和备料同步更新。撤销一个方案保留份数、其他方案和笔记。保存快照不随目录或规则更新静默变化。

### 6.2 私人自建配方

用户可从空白新建，或复制参考配方为私人配方。P0 使用结构化表单与现有材料/器具目录，不开放任意公式、脚本或 HTML。目录外需求可写普通文本提示，但不得进入自动换算或替代判断，也不得让用户误认为已经获得可靠单位转换。

字段至少含名称、基础份数、材料及是否可选、数量和单位、器具、步骤、调配时间与前置时间说明、来源说明。草稿允许不完整；进入制作或加入备料前检查必需字段、非负有限数值和步骤引用，定位错误且保留输入。没有项目规则的材料不能自动给出替代方案。

单机 P0 图片使用现有目录图或默认图，自建内容不能自动借用别的饮品图冒充实物；目录图/AI 图标识可见。任意图片上传不属于 P0。

### 6.3 私人配方合集

用户创建标题、可选说明、封面（现有图或默认图）和有序配方条目。合集可包含参考配方与自己的版本；保存时记录配方快照及其版本。编辑原配方后提示合集引用了旧版本，由用户明确更新，不能偷偷替换。

同一合集每个配方版本只保留一条；新增重复项时提示已有位置。P0 每个合集最多 50 条，每位用户最多 100 个合集，作为初始产品上限，后续可调整。空合集允许作为私人草稿；合集制作时选择单杯或明确加入备料，不默认一次制作整份合集。

删除合集不删除配方；移除条目不删除原始做法。删除或恢复数据前说明影响，受影响的合集条目使用已保存快照继续可读，或明确提示缺失，不出现空按钮。

### 6.4 服务器保存与迁移

SQLite 事务提交后才展示已保存，WAL 与 FULL 同步。读取、磁盘、网络或写入失败保留原数据和页面修改，提供导出重试；不得用空数据覆盖损坏记录。多个页面和设备比较版本，冲突由用户明确选择。

数据库默认 data/onecup.sqlite；Docker 为 /data/onecup.sqlite，命名卷 onecup_personal_data。记录包含收藏、库存、器具、做法、自建配方、合集、备料、咖啡记录与主题。没有账号或会话。清理浏览器不影响服务器记录，远程访问共用同一工作区；恢复替换影响所有连接设备。

## 7. 数据模型与迁移

| 对象 | 必需信息 |
| --- | --- |
| RecipeDefinition | 稳定 ID、来源类型、内容版本、材料/单位/规格、器具、步骤引用、耗时、验证状态、图片性质 |
| PersonalVersion | 当前完整配方快照、用量、份数、替代及撤销信息、私人名称/笔记、更新时间 |
| RecipeCollection | ID、名称、说明、有序条目、各条目的固定快照版本、更新时间 |
| Workspace | 收藏、库存、器具、私人配方、合集、做法、备料、咖啡记录、主题及格式版本 |

当前 UserData.schemaVersion=2，v1 导入校验后补全自建配方与合集；v2 导入完整校验新字段，损坏或不支持的格式不覆盖现有记录。合集条目保存独立完整快照，源删除仍可读。

OSS 核心模型不含公开作者档案、发布状态、审核状态、关注关系或分享 token。外部来源说明可保留配方来源地址，但不抓取作者社交资料，也不自动发网请求。

## 8. 错误与边界状态

- 无搜索结果：解释当前条件并可清空，单候选随机不伪装成多候选。
- 图片失败：占位及重试，不阻断材料和步骤。
- 规则不适用：不显示操作入口；目录外材料不推断等效。
- 无效输入：标出对应材料、数量或步骤，草稿可保存。
- 文件格式不支持、损坏、超限：拒绝导入，现有数据保持不变。
- 服务器数据库不可用：显示读取/保存错误，保留原数据，不提供虚假的成功提示或登录补救入口。
- 公开接口请求：OSS 服务无该路由；构建不加载社交模块，不依赖前端隐藏实现隔离。

## 10. 开源发布门槛

1. O01–O11 按上述范围验收；没有登录或访问自营服务的强制依赖。
2. 提供干净环境变量说明、Compose 配置、示例目录和迁移说明。排除实际 account/database ID、域名运营配置、凭据、真实 SQLite、D1 导出、日志、用户备份及 `.private` 内容。
3. 确认代码许可证、配方文本和每项图片的可再分发范围；无法确认的素材用有明确来源的替代品或占位图，不能因为可在自营站显示就默认可公开分发。
4. 产物不含账号 API、账号数据库、明文密码测试或邮件配置；包含单用户 SQLite API 与持久数据卷。保留导出恢复及旧记录迁移。
5. 安装、构建、测试、部署、导出和恢复可复现；公开贡献、问题报告和支持方式只指向项目渠道，不放个人社交联系方式。

## 11. 推进与取舍

先抽离共用核心和独立单机入口，再完善自建与合集，最后完成服务端部署、Docker 和公开材料检查。跨版本的制作缺陷优先修在共同核心。暂不建设公共社区，不借“支持分享”的名义增加社交字段、匿名公开托管或公开用户目录。
